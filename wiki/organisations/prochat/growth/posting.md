# ProChat Posting System

**Status:** canonical manual publishing standard  
**Owner:** Steve Westhoek  
**Last updated:** 2026-07-01

## Purpose

Define how ProChat drafts, reviews, publishes, and learns from posts across professional and social channels.

Every post must belong to exactly one publishing lane:

```text
ProChat Memory for QA
ProChat Workbench
```

Publishing remains manual, review-first, and evidence-aware.

## Shared workflow

1. Select one product lane.
2. Define one audience and one objective.
3. Identify the real evidence or approved source.
4. Draft one primary post.
5. Review claims, privacy, tone, and product boundaries.
6. Edit in Steve’s natural voice.
7. Publish manually only after explicit approval.
8. Record useful feedback and product learning.

No system may post, schedule, reply, or message automatically under this strategy.

## Publishing lane 1 — ProChat Memory for QA

### Purpose

Support:

- QA domain credibility;
- selected beta recruitment;
- practical demonstrations;
- structured feedback;
- evidence-based case studies;
- QA network development.

### Primary audiences

- individual QA testers;
- QA engineers;
- QA leads;
- test managers;
- QA businesses evaluating future tester licenses.

### Approved content angles

- a recurring test failure and the lesson worth preserving;
- what evidence helped rule causes in or out;
- why current evidence overrides stored memory;
- how a reviewed lesson can help a later investigation;
- how local Markdown and Git support inspectable memory;
- sanitization and project-scope boundaries;
- a real beta onboarding or retrieval lesson;
- an approved tester observation;
- a case-study question that still requires evidence.

### Approved calls to action

- Explore ProChat Memory for QA
- Join the selected QA beta
- Try it with one recurring QA failure
- Share a QA investigation pattern you keep repeating
- Provide structured feedback on the local workflow

### Required beta language

When relevant, make clear that:

- the product is in active beta development;
- beta participation is selected;
- the beta is free and has no fixed end date;
- customer and client memory remains local;
- licensing is not yet final;
- human review remains required.

## Publishing lane 2 — ProChat Workbench

### Purpose

Support:

- qualified GitHub discovery;
- real-project demonstrations;
- builder adoption;
- installation and onboarding;
- product feedback;
- responsible workflow comparisons.

### Primary audiences

- developers;
- builders;
- technical founders;
- vibe coders;
- people already using ChatGPT for project work.

### Approved content angles

- giving ChatGPT exact local project context;
- a guarded file change on a real repository;
- targeted validation after a change;
- explicit-path Git staging or commits;
- protecting unrelated worktree changes;
- persistent project work and handoffs;
- installation and source-connection lessons;
- a failed validation and bounded repair;
- a clear product release or documentation improvement;
- workflow comparisons using specific criteria.

### Approved calls to action

- Explore ProChat Workbench
- View the project on GitHub
- Review the installation guide
- Connect ChatGPT to a local project
- Try one guarded task on a real repository
- Share an onboarding or workflow problem

### Comparison boundary

Posts may compare Workbench with Cursor, Claude Code, and similar tools when the comparison is specific and fair.

Useful criteria include:

- reasoning interface;
- access to local context;
- execution boundaries;
- validation;
- Git control;
- onboarding;
- workflow continuity;
- plan or usage constraints.

Do not claim universal replacement, unlimited usage, zero hallucinations, guaranteed lower cost, or superior performance in every workflow.

## Post structure

Use the smallest structure that communicates the point clearly.

A strong default is:

```text
real problem
→ observed evidence
→ useful lesson or demonstration
→ limitation or review boundary
→ relevant next action
```

Other acceptable structures:

```text
observation → distinction → question
```

```text
before → guarded workflow → verified result
```

```text
failed assumption → evidence → corrected lesson
```

## Evidence rules

Every factual product or user claim must be supported by at least one of:

- approved product documentation;
- a sanitized real demonstration;
- a verified repository or release change;
- approved user feedback;
- a measured result with a documented method;
- a clearly labeled personal observation.

When evidence is incomplete, write it as a question, hypothesis, or planned experiment.

Do not invent:

- users;
- customers;
- testimonials;
- quotes;
- usage numbers;
- time saved;
- accuracy improvements;
- cost savings;
- product capabilities;
- competitor behavior.

## Style

Posts should be:

- clear;
- practical;
- direct;
- calm;
- specific;
- useful without requiring a product pitch;
- honest about uncertainty and beta maturity.

Avoid:

- hype;
- vague transformation claims;
- engagement bait;
- false urgency;
- manufactured controversy;
- generic advice unrelated to either product;
- architecture before user value;
- unsupported statistics;
- hostile competitor language.

## Platform adaptation

Adapt the same verified idea to the platform rather than generating unrelated volume.

### LinkedIn

Use practical professional observations, lessons, demonstrations, and questions.

### X

Use one concise insight, boundary, or workflow lesson. Threads are optional.

### Reddit and communities

Lead with the problem, evidence, and discussion value. Follow community rules and avoid disguised promotion.

### GitHub

Use release notes, demonstrations, documentation improvements, issues, and discussions tied to actual product behavior.

## Manual review checklist

Before publishing, confirm:

- exactly one product lane is selected;
- the intended audience is clear;
- the evidence source exists;
- private or client information is absent;
- product claims match current behavior;
- future capabilities are not presented as current;
- beta language is accurate where relevant;
- the call to action fits the lane;
- the post is useful without exaggeration;
- comparisons are specific and fair;
- publishing will be manual.

## Learning record

After publishing, capture useful signals such as:

### ProChat Memory for QA

- tester questions;
- recurring QA language;
- beta interest and fit;
- trust or privacy concerns;
- demonstration feedback;
- case-study evidence;
- onboarding and retrieval problems.

### ProChat Workbench

- GitHub discovery quality;
- installation questions;
- real-project adoption;
- workflow objections;
- comparison questions;
- documentation gaps;
- product feedback.

Likes, impressions, followers, and reposts may be recorded, but they do not prove retained product value.

## Core principle

```text
Evidence before claims.
Review before publishing.
Learning before scale.
```
