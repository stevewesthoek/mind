# ProChat QA Memory — v0.1 Implementation Plan

**Status:** starter implementation plan  
**Owner:** Steve Westhoek  
**Purpose:** define the leanest useful first build of ProChat QA Memory.

## 1. Implementation goal

Build a small, usable, licensed repo product that proves the core idea:

```text
Every failed test can become reusable QA memory.
```

v0.1 should be useful without an API, server, dashboard, CLI, database, extension, pipeline integration, or access to client systems.

## 2. v0.1 success criteria

v0.1 is successful when a tester can:

1. Clone or copy the ProChat QA Memory repo.
2. Create a local project/client memory workspace.
3. Paste a failed test log or tester note into the workflow.
4. Use any AI assistant to draft a failure summary and reusable lesson.
5. Review and sanitize the output.
6. Save the lesson into the correct scoped memory file.
7. Reuse that memory in a later triage or test planning task.

## 3. Build principles

- Build memory first.
- Build the smallest useful workflows.
- Avoid tool-specific dependencies.
- Keep everything readable in markdown.
- Use manifests only where they make structure clearer.
- Keep client data out of the product repo.
- Make the first demo obvious.

## 6. First workflow: failed test to reusable lesson

This is the highest-priority v0.1 workflow.

Input:

- failed test name
- framework/tool
- environment
- error/log excerpt
- screenshot/trace/report link where available
- tester notes
- related memory files

Output:

- failure summary
- likely category
- evidence used
- next action
- reusable lesson
- suggested memory file
- sanitized memory update

Failure categories:

- product bug
- test automation bug
- flaky test
- selector/locator issue
- test data issue
- environment issue
- pipeline/infrastructure issue
- timing/synchronization issue
- permission/authentication issue
- unclear / needs investigation

## 8. First AI instruction pattern

The generic instruction should say:

```text
Use QA memory as evidence, not authority.
Current logs, screenshots, traces, source code, test output, and tester judgment override stored memory.
Do not write trusted memory automatically.
Draft a memory update for human review.
Keep client-specific details scoped to the correct client/project memory.
Sanitize any lesson before promoting it to cross-project memory.
```

## 16. NotebookLM Research Report: ProChat QA Memory v0.1 Implementation Analysis

This section contains research findings from NotebookLM analysis of the v0.1 implementation plan against the product spec and industry benchmarks (agent-qa, QASkills, GitHub Copilot instructions, and OWASP memory guidance).

### 16.1 Keep

The following elements from the v0.1 plan are well-grounded and align with core principles:

- **The "Review-First" Manual Workflow:** The "Failed Test to Reusable Lesson" workflow is the highest priority and correctly emphasizes human intervention. This aligns with OWASP Agent Memory Guard principles, which advocate for review and sanitization to prevent memory poisoning.

- **Markdown-First Architecture:** Maintaining all memory, skills, and workflows as readable markdown files ensures portability and tool-agnosticism. This mirrors the GitHub Copilot pattern of repo-native instructions (`.github/copilot-instructions.md`).

- **Scope Separation:** The distinction between client-specific (local) and cross-project (global) memory is critical for security and privacy.

- **Zero-Dependency Build:** Prioritizing a product that works without an API, CLI, or database ensures it is immediately useful for the primary buyer (freelance testers and agencies) who may lack administrative access to client environments.

### 16.2 Add

To strengthen the plan and bridge specificity gaps, the following should be added:

- **Metadata Discipline (from QASkills):** While manifests are mentioned, v0.1 needs a strict **Frontmatter Standard** for all `.md` files (e.g., `id`, `version`, `author`, `last_reviewed`, `source_reference`) to ensure the "Source-traceable" principle is actionable. Example frontmatter:

```yaml
---
id: skill-analyze-failed-test
version: 0.1.0
author: Steve Westhoek
last_reviewed: 2024-05-20
source_reference: ProChat QA Memory v0.1
---
```

- **Sanitization Checklist:** Explicitly define what must be stripped before promoting a lesson to global memory. Critical items:
  - Internal hostnames (e.g., `staging-01.company.com` → `staging environment`)
  - Specific selector IDs (e.g., `#elem-12345` → `form input selector`)
  - IP addresses and internal URLs
  - PII (usernames, email addresses, phone numbers)
  - Client-specific project names

- **Conflict Resolution Guidance:** Basic instructions on using Git to manage memory "merges" when multiple testers contribute to the same shared memory repo. Recommendation: use feature branches for local edits, rebase conflicts during review.

- **"System Prompt" Templates:** Specific markdown files containing the foundational instructions for different AI assistants (ChatGPT, Claude, etc.) to ensure they respect the memory scopes. Store in `core/ai-instructions/`.

### 16.3 Remove / Postpone

The following elements should be deferred to v0.2+ to maintain a lean v0.1:

- **Multiple Demo Cases:** Reduce the "Fake Webshop Demo" from three cases to **one comprehensive case**. Proving the *workflow* for a single complex failure (e.g., a flaky timing issue) is more valuable for a pilot than volume.

- **Complex Skill Files:** Limit v0.1 to exactly **three starter skill files** as originally planned, avoiding "feature creep" into specialized performance or API testing skills until the core failure-analysis loop is validated.

- **Automated Ingestion:** Any form of CI log ingestion or "automatic" drafting should remain strictly out-of-scope to focus on the human-reviewed "Memory-first" foundation.

### 16.4 Clarify

The current plan lacks specificity in these areas:

- **Physical Repo Relationship:** It is unclear if the "Client Memory" should be a sub-folder of the product repo, a separate repo, or a symlinked directory. Recommendation: v0.1 should assume client memory lives in a **separate directory** (not inside the product repo). Users can symlink or compose them as needed.

- **The "Promotion" Mechanism:** The spec mentions a "promotion path" but does not define the manual steps. Precise procedure for v0.1:
  1. Draft lesson in `client-memory/drafts/`
  2. Sanitize (strip client-specific details)
  3. Copy sanitized content to `prochat-qa-memory/memory/` file
  4. Commit with message: `docs: promote [lesson-name] to global memory (source: [client-name])`

- **AI Context Loading:** Does the user manually paste the content of memory files into the AI chat, or is the intention for the user to use an IDE (like Cursor) that indexes the local folder? Recommendation for v0.1: **Users manually copy/paste** memory content into AI chat. Document this clearly in QUICKSTART.

### 16.6 v0.1 Acceptance Criteria

v0.1 is complete and ready for pilot when:

1. **Portability Verified:** The repo can be cloned and used in a standard markdown editor (VS Code, Cursor, Obsidian) without any installation, environment variables, or dependencies.

2. **Workflow Success:** A tester can transform a raw log into a sanitized, reviewed lesson in under 5 minutes using the provided workflow and skills with any major LLM (GPT-4, Claude 3, or GitHub Copilot).

3. **Safety Compliance:** The `core/safety-rules.md` explicitly defines a "Sanitization Checklist" that prevents PII and client-specific data from entering global memory. Include concrete examples of what must be stripped.

4. **AI-Agnostic:** The starter skills are confirmed to work with at least **two major LLMs** (e.g., GPT-4 and Claude 3) without modification.

5. **Metadata Standardized:** Every file in the `memory/` and `skills/` directories includes a valid YAML frontmatter block with `id`, `version`, `author`, `last_reviewed`, and `source_reference` fields.

6. **Demo Clarity:** A new user can understand the value proposition by reading `demo/README.md` and following the single comprehensive walkthrough in under 10 minutes.

7. **Documentation Complete:** README, QUICKSTART, workflow guides, and AI instructions are clear enough that a tester with no QA memory experience can onboard independently.

### 16.7 v0.2 Candidates

These features are deferred to v0.2+ to maintain focus on the core memory layer:

- **CLI Tooling** — For automating manifest creation, validation, and sanitization checks. Rationale: Avoid build-complexity in v0.1; manual editing keeps the barrier to entry low.

- **GitHub Action** — To validate manifest schemas and safety rules on PR. Rationale: v0.1 is for manual, tool-agnostic use; CI integration comes later.

- **Vector Database / RAG Integration** — For large-scale memory retrieval and semantic search. Rationale: Portable markdown files are sufficient for initial pilot volumes; search needs emerge at scale.

- **Multi-tenant Workspace Manager** — For testers managing 5+ clients simultaneously. Rationale: v0.1 should focus on the single-tester, single-client experience first; multi-client orchestration is a v0.2 expansion.

- **Web Dashboard** — Any browser-based UI for viewing, editing, or sharing memory. Rationale: Stays out-of-scope per product definition; markdown files + Git remain the interface.

- **Automatic Memory Deduplication** — ML-based or heuristic-based detection of duplicate lessons. Rationale: Human judgment is required during early pilots; automation follows evidence.

### 16.8 Key Implementation Risks and Mitigations

| Risk | Mitigation |
|------|-----------|
| **Memory Poisoning:** AI-generated false lessons pollute persistent memory. | Strict review-first gate; never promote AI output without human approval. Enforce via workflow and training. |
| **Privacy Leaks:** Client-specific data accidentally promoted to global memory. | Pre-commit hook or checklist; example: validate no client names, IPs, or hostnames in global files. Include in demo walkthrough. |
| **Tester Confusion:** Unclear which memory to use when (client vs. project vs. global). | Provide side-by-side comparison in QUICKSTART; use `core/principles.md` to explain scoping rules with concrete examples. |
| **Limited AI Context:** Long memory files may exceed AI token limits. | Keep individual memory files under 2000 tokens; split by theme (e.g., separate `login-failures.md` from `performance-lessons.md`). |
| **Git Workflow Friction:** Testers unfamiliar with Git may struggle with merges. | Recommend simple branching (feature branches for edits, rebase on main); document in `core/git-workflow.md` for v0.1. |
