# ProChat QA Memory — v0.1 Implementation Plan

**Status:** refined v0.1 implementation plan  
**Owner:** Steve Westhoek  
**Purpose:** define the leanest executable first build of ProChat QA Memory.

## 1. Implementation goal

Build a small, usable, licensed repo product that proves the core idea:

```text
Every failed test can become reusable QA memory.
```

v0.1 should be useful without an API, server, dashboard, CLI, database, extension, pipeline integration, or access to client systems.

## 2. v0.1 success criteria

v0.1 is successful when a tester can:

1. Clone or copy the ProChat QA Memory repo.
2. Create a local project/client memory workspace outside the product repo.
3. Paste a failed test log or tester note into the workflow.
4. Use any AI assistant to draft a failure summary and reusable lesson.
5. Review and sanitize the output.
6. Save the lesson into the correct scoped memory file.
7. Reuse that memory in a later triage or test planning task.

## 3. Build principles

- Build memory first.
- Build the smallest useful workflows.
- Avoid tool-specific dependencies.
- Keep everything readable in markdown.
- Use frontmatter and manifests only where they make structure clearer.
- Keep client data out of the product repo.
- Make the first demo obvious.
- Treat memory as evidence, not authority.
- Promote memory only after human review.
- Treat folders as storage, not the product itself.
- Build the v0.1 engine through standards, memory maps, AI instructions, evidence rules, and review-gated workflows.
- Make onboarding black-box and natural-language first.
- Make the communication layer proactive: the assistant should explain when memory is active, when it sees a pattern, when it recommends a memory update, and when existing memory changed the next best action.
- Keep self-improvement review-gated in v0.1: the assistant may detect, draft, recommend, and maintain, but trusted writes require approval.

## 5. Physical repo relationship

This must be clear from day one.

```text
qa-memory-system/
  prochat-qa-memory/      # licensed product repo
  qa-workspaces/          # user's local/company-approved workspaces
    client-a/
    client-b/
    cross-project/
```

The product repo and workspace should be siblings under one parent folder. This keeps relative-path examples predictable while preventing private client memory from living inside the licensed product repo.

The product repo contains:

- core method
- workflows
- skills
- templates
- safety rules
- demo material
- generic cross-project examples

The workspace contains:

- client-specific context
- project-specific failures
- local drafts
- private notes
- reviewed memory for a specific client or project

Client-specific memory should not be committed into the product repo.

## 8. First workflow: triage to lesson

This is the highest-priority v0.1 workflow.

Input:

- failed test name
- framework/tool
- environment
- error/log excerpt
- screenshot/trace/report link where available
- tester notes
- relevant memory files

Output:

- failure summary
- likely category
- evidence used
- next action
- reusable lesson
- suggested memory file
- sanitized memory update

Failure categories:

- product bug
- test automation bug
- flaky test
- selector/locator issue
- test data issue
- environment issue
- pipeline/infrastructure issue
- timing/synchronization issue
- permission/authentication issue
- unclear / needs investigation

## 9. Manual v0.1 workflow steps

1. Copy the relevant failed test input into `inbox/failed-test-input.md` or equivalent local note.
2. Select relevant memory files manually.
3. Paste the failed input and selected memory context into the AI assistant.
4. Ask the AI to draft the triage, category, next action, and memory update.
5. Review the answer against current evidence.
6. Sanitize client-specific details.
7. Save the reviewed lesson into the correct scoped memory file.
8. Promote only generalized lessons to cross-project memory.
9. Commit the change if the workspace uses Git.

## 10. First AI instruction pattern

The generic instruction should say:

```text
Use QA memory as evidence, not authority.
Current logs, screenshots, traces, source code, test output, and tester judgment override stored memory.
Do not write trusted memory automatically.
Draft a memory update for human review.
Keep client-specific details scoped to the correct client/project memory.
Sanitize any lesson before promoting it to cross-project memory.
```

## 11. Starter skills

v0.1 should include exactly three starter skills.

### 11.1 `analyze-failure.SKILL.md`

Purpose:

```text
Analyze a failed test using selected QA memory and produce a concise triage draft.
```

### 11.2 `sanitize-lesson.SKILL.md`

Purpose:

```text
Convert a client-specific lesson into a safe generalized lesson for cross-project memory.
```

### 11.3 `draft-memory-update.SKILL.md`

Purpose:

```text
Draft a reviewed-memory update in the correct format and scope.
```

## 12. Frontmatter standard

Every memory, workflow, and skill file in v0.1 should include YAML frontmatter.

```yaml
---
id: unique-slug
scope: personal|client-project|cross-project|company-approved
status: raw|draft|reviewed|trusted|deprecated
created: YYYY-MM-DD
source_ref: sanitized-source-or-origin
---
```

## 13. Sanitization checklist

Before promoting any lesson to cross-project memory, remove or generalize:

- client names
- internal hostnames
- internal URLs
- IP addresses
- usernames
- email addresses
- tokens and secrets
- exact private selectors when they reveal internal naming
- project-specific architecture names
- confidential logs
- screenshots with private data

Example:

```text
Unsafe: Login failed on staging-01.clientname.com because auth-service-prod-eu returned 401.
Safe: Login failures can be caused by stale test users or auth service issues in staging environments. Verify test-user freshness and auth availability before classifying as product regression.
```

## 14. Conflict and precedence guidance

When multiple memories could apply, use this order:

```text
current evidence
→ test-case memory
→ suite memory
→ project memory
→ client/team memory
→ cross-project memory
→ personal heuristics
```

If memory conflicts with current evidence, current evidence wins.

If project memory conflicts with cross-project memory, project memory wins for that project.

If a memory entry is outdated, mark it as deprecated rather than deleting it immediately.

## 15. Git workflow guidance

v0.1 should not require advanced Git skills, but the product should include simple guidance.

Recommended pattern:

```text
main = trusted memory
branch = draft/review memory update
pull request or review = human approval
merge = promoted trusted memory
```

For solo/freelance testers, a simple local commit history is enough.

For teams, use branches or pull requests for shared memory updates.

## 16. Demo build

Build one focused demo case first:

```text
FakeShop login selector failure
```

Why this case:

- easy to understand
- shows brittle automation pain
- demonstrates memory-specific advice vs generic AI advice
- avoids needing a real test runner
- makes the value visible in 10 minutes

Payment and checkout examples can be referenced as future cases, but the live v0.1 demo should stay focused.

## 17. Validation checklist

v0.1 is ready for pilot when:

- the repo can be cloned and read in VS Code, Cursor, Obsidian, or any markdown editor
- no install or environment setup is required
- a tester can understand the product in 10 minutes
- a tester can turn a raw failed test into a sanitized reviewed lesson in under 5 minutes
- the external workspace model is clear
- the project/client/cross-project memory distinction is clear
- every memory and skill file has valid frontmatter
- safety rules include concrete sanitization examples
- the first demo proves the before/after value
- the workflow works with at least two major AI assistants without major changes

## 18. First pilot plan

Pilot with one tester for two weeks.

Use only:

- `triage-to-lesson.md`
- `analyze-failure.SKILL.md`
- `sanitize-lesson.SKILL.md`
- `draft-memory-update.SKILL.md`
- `known-failures.md`
- `flaky-tests.md`
- `failure-patterns.md`
- `general-qa-lessons.md`

Measure:

- number of failures captured
- number of reviewed lessons created
- repeated investigation avoided
- time saved
- whether AI answers became more specific
- whether project/client separation was clear
- whether the workflow felt too heavy
